# Лаб 6. TypeScript для протоколу і симуляції (`strict` + `Zod` + Branded Types)

Міграція мультиплеєрної 2D-гри з лаби 5 (авторитетний сервер 30 Гц, клієнтське передбачення, звірка стану, інтерполяція чужих сутностей та бінарний протокол `DataView`) на **строгий TypeScript (`strict: true`, `noUncheckedIndexedAccess: true`)** із рантайм-валідацією вхідних пакетів через **Zod**.

## 1. Які помилки знайшов TypeScript під час переведення з JS

Під час поступового перейменування файлів `.js` → `.ts` із увімкненими прапорцями `strict: true` та `noUncheckedIndexedAccess: true` компілятор `tsc` виявив 5 реальних класів помилок, які в JavaScript залишалися прихованими:

1. **Підміна числових ідентифікаторів (`InputSeq` vs `TickNumber` vs `ClientBulletSeq`):** у JS номер кроку сервера (`serverTick`), порядковий номер команди клієнта (`seq`) та локальний номер кулі (`clientBulletSeq`) були звичайними `number`. Після введення branded-типів `tsc` підсвітив місце під час дедуплікації куль, де `InputSeq` порівнювався з `ClientBulletSeq`.
2. **Небезпечне звернення до елементів масиву за індексом (`noUncheckedIndexedAccess`):** при виборі точки спавну `SPAWN_POINTS[slotIndex]` та під час інтерполяції між двома сусідніми знімками `buf[i]` і `buf[i + 1]` TypeScript показав, що елемент може бути `undefined` при виході за межі масиву. Довелося додати явні перевірки меж і безпечні значення за замовчуванням.
3. **Випадкова мутація координат вектора (`readonly Vec2`):** у фізиці корабля та куль проміжні обчислення іноді змінювали поля `x` та `y` існуючого об'єкта замість створення нового вектора. Модифікатор `readonly` на полях `Vec2` змусив перевести кінематику (`integrateKinematics`, `resolveObstacleCollisions`) на чисті функції без побічних ефектів.
4. **Необроблені варіанти повідомлень у `switch` (`never`):** додавання службових повідомлень (`protocol_ack`, `error`) у `ServerMessage` одразу викликало помилку компіляції в клієнтському `switch (msg.type)` через охоронець `assertNever(msg)` у гілці `default`.
5. **Неперевірені вхідні дані з мережі та `process.env`:** заміна `any` на `unknown` у `parseClientMessage(raw: unknown)`, у блоках `catch (err: unknown)` та при зчитуванні `process.env.PORT` змусила пропустити всі зовнішні межі процесу через схеми Zod замість ручних перевірок `typeof`.

## 2. Три типи простими словами

* **`unknown` (Невідомий тип):** це безпечна заміна для `any`. Якщо змінна має тип `unknown`, TypeScript забороняє читати її поля або викликати як функцію, доки ви явно не перевірите її структуру в рантаймі (наприклад, через `Schema.safeParse(data)` або `err instanceof Error`). Це ідеальний тип для даних із WebSocket, `JSON.parse` та блоків `catch`.
* **`never` (Неможливий тип):** це тип значень, яких ніколи не повинно існувати під час виконання програми. У конструкції `switch` по об'єднанню з полем `type` або `kind`, якщо ми обробили всі відомі варіанти, у гілці `default` змінна звужується до типу `never`. Якщо пізніше додати новий тип повідомлення і забути додати для нього `case`, `tsc` одразу видасть помилку компіляції.
* **Branded-типи (Номінальні «брендовані» типи):** у TypeScript типізація за замовчуванням структурна — два `number` вважаються однаковими, навіть якщо один означає ID кулі, а інший — номер кадру. Branded-тип додає до примітиву віртуальну мітку на етапі компіляції (`Brand<number, 'InputSeq'>`), яка не існує в рантаймі й не витрачає пам'ять, але не дозволяє передати `TickNumber` туди, де функція очікує `InputSeq`.

## 3. Чому фреймворк для UI взяли або ні

Для рендерингу арени (`renderer.ts`) та ігрового циклу (`main.ts`) фреймворк не використовувався за умовою завдання, оскільки фіксований крок симуляції (`30 Гц`) та малювання кадрів на `<canvas>` (`60+ FPS`) потребують прямого контролю над `requestAnimationFrame` без накладних витрат на звірку Virtual DOM.

Для лобі, чату та панелі телеметрії ми **також свідомо не підключали React, Vue або Svelte**, а реалізували їх на чистому строго типізованому TypeScript (`client/main.ts` із типізованою обгорткою `getRequiredElement<T>`). Причини:
1. **Єдиний пайплайн збірки без бандлера:** увесь проєкт (`shared/`, `server/`, `client/`, `tests/`) компілюється одним викликом `tsc` у стандартні ES-модулі, які браузер завантажує напряму без Webpack чи Vite.
2. **Мінімальний розмір і швидкий CI:** у `dependencies` залишаються лише `ws` та `zod`, тому встановлення пакетів і перевірка `npm run typecheck` у CI займають лічені секунди.
3. **Низька частота оновлення DOM:** список кімнат, склад гравців і чат оновлюються лише за рідкісними подіями (`room_list`, `roster_update`, `chat`), тому реактивний фреймворк тут не дає виграшу в продуктивності, але ускладнює конфігурацію.
